# How this workspace is organized

This directory is a **prov workspace** conforming to **prov/1**.

Its structure is not imposed by the filesystem. Every document declares its own
links inside its metadata block, and the whole workspace unfolds by following
them from a single root. That means you can read it with nothing but a text
editor, and you can write a reader for it from this page alone.

This file was generated by prov and is rewritten from the workspace's own
configuration. Edits to it will be overwritten — change `prov.yaml` instead.

---

## 1. The bootstrap rules

A reader that knows only these rules can traverse any prov/1 workspace.

1. **Find the root.** In this directory, a *root candidate* is a file that has a
   metadata block (rule 2) and declares no `part_of` field. If more than one
   qualifies, prefer the one whose filename stem is `index`, then `readme`. If
   several remain and none is so named, the root is ambiguous — stop rather than
   guess.

   `part_of` is spelled literally here, whatever this workspace calls its own
   relations (§3). Finding the root is what tells you the vocabulary, so it
   cannot depend on knowing it.

2. **Read its metadata block.** A document is a metadata block plus a body. The
   block is separated from the body by a fence at the top of the file — `---`
   for YAML, `;;;` for JSON, or an opening ```` ```fig ```` line. A file whose
   extension is `.yaml`, `.yml`, `.json`, `.toml`, `.fig`, or `.figl` is
   metadata all the way down and has no body. Either way the block is a
   key → value map, and key order is meaningful to people, not to machines.

3. **Read `spec`.** An integer naming which version of these rules applies. This
   workspace declares `spec: 1`. A higher number than you know means the
   structure rules (1, 2, 4, 5) still hold and you may still traverse; treat
   settings you do not recognize as opaque rather than wrong.

4. **Read the vocabulary.** `spanning` names the one relation that forms the
   containment spine; `relations` declares what each relation field means, its
   cardinality, and its reciprocal. Both are reproduced in §3 below. A workspace
   that declares neither uses `contents`/`part_of` containment with `contents`
   spanning.

5. **Unfold.** From the root, follow the field named by `spanning` to reach its
   children; each child's own block repeats the process. Every node is reachable
   from the root by exactly one such path. All other relations are an overlay
   graph laid over that spine — follow them for meaning, never for discovery.

Everything past rule 3 is learned from the documents, not known in advance. That
is what lets the vocabulary differ between workspaces without a reader having to
know yours beforehand.

## 2. Reading a reference

A relation's value is one reference, or a list of them. Three spellings are
recognized, and you may encounter all three in one workspace:

| written | called |
| --- | --- |
| `[Some Title](path/to/doc.md)` | a markdown reference — the label is decoration, the target is in the parens |
| `[[path/to/doc.md]]` or `[[target\|Label]]` | a wikilink |
| `path/to/doc.md` | a bare target |

Resolve the target by its own syntax, in this order:

- Contains `://`, or starts with `mailto:` — **external**. Never resolved.
- Starts with `id:` — an **identity handle**. Look up the remainder in the
  registry (§5) to get a path. Never resolve it as a path.
- Starts with `/` — a path relative to **this directory**, the workspace root.
  It is not an absolute filesystem path.
- Anything else — a path relative to the **directory of the document you read it
  from**.

Fold `.` and `..` lexically; do not follow symlinks. A path that still escapes
the workspace root after normalizing is invalid, not a reference outward.

A target that names no file is a broken link — a fact to report, not a reason to
stop unfolding.

## 3. This workspace's vocabulary

The spine is **`contents`**. Follow it from the root to reach every document.

| relation | means | cardinality | reciprocal |
| --- | --- | --- | --- |
| `contents` | documents contained by this one | many | `part_of` |
| `part_of` | the document that contains this one | one | `contents` |
| `links` | arbitrary cross-references to other documents | many | `link_of` |
| `link_of` | documents that cross-reference this one | many | `links` |

Reciprocals are maintained in both directions: if A lists B under `contents`,
B lists A under `part_of`. A missing half is a repairable inconsistency, not a
different meaning.

`part_of` is single-valued, which is what makes the spine a tree with one root.
A document that belongs to several things expresses that through `links` or
another non-spanning relation.

No controlled vocabularies are declared. Every field not named above is content
this workspace carries and prov never interprets.

## 5. Content, machinery, and payloads

Every node in the graph is a plaintext document with a metadata block. Anything
else is *referenced* from a node rather than being one, and the field it is
referenced by tells you what it is.

- **Content** — reached by a relation (§3). In the spine, reciprocal maintained,
  can carry an id.
- **Machinery** — reached one way from the root by a named pointer: `config`
  points at this workspace's settings, `registry` at the id → path table,
  `recycle_bin` at the deleted-items index, `about` at this file. Machinery
  declares no `part_of` and is not part of the containment tree; that is why
  following `contents` never reaches it, and why its absence from the tree is
  not an error.
- **Payloads** — a binary is never a node. It is wrapped: a small metadata
  document names it in a `content` field, and that document is the node. The
  graph stays entirely plaintext.

This workspace links `config` → `prov.yaml`. No registry or recycle bin has been
created yet; both appear as root pointers when first needed.

## 6. What is safe to edit

Everything here is plain text and yours. Two cautions, both about fields prov
maintains and must be able to parse back:

- **`id`, and the registry's contents.** An id is a durable handle something
  else may already depend on. Ids are never reissued, even after deletion.
- **`content_hash`.** A checksum of the referenced bytes, written as
  `sha256:<hex>` so any tool can verify it independently.

Relation fields are safe to edit by hand — that is the point of keeping them in
the documents. Edit one half of a reciprocal pair and the other half becomes
repairable, not lost.
